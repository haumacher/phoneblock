# Dongle localized assets (issue #460)

Source of truth for the dongle's localized **answer-bot announcement audio**,
the **dialog clips** of the interactive answer bot, **status-mail strings**, and
**web-UI strings**. The firmware carries no
per-language payload — assets are published to the CDN and pulled on demand
(see `main/i18n_sync.c`, `main/mail_i18n.c`, the loader in
`main/web/index.html`): the string packs co-located with the firmware
release, the audio in its own channel, versioned by the audio format only
(see "Audio channel").

Everything is **committed to git and translated during development**. Nothing
is translated at release time.

## Files

- `languages.txt` — one locale code per line (the `ui_lang` the UI selects /
  the device stores). Add a line to add a language.
- `audio/announcement-<lang>.alaw` — **committed announcement recordings**
  (raw G.711 A-law, 8 kHz mono — exactly what the device streams, the same
  format as the old single `main/audio/announcement.alaw`). Hand-record or
  synthesize each however you like and drop it here; `audio-assets.sh` uses
  it verbatim (a `.wav`/`.mp3`/`.m4a`/`.flac` is converted with ffmpeg). When
  both a `.alaw` and a source recording (e.g. `announcement-<lang>.mp3`) are
  committed, the `.alaw` is used verbatim and the source is kept only for
  re-encoding. A language with no recording ships **text-only** (the device
  answers silently).
- `audio/announcement-<lang>.txt` — the **transcript of the recording next to
  it**, co-located with the `.alaw`. Keep it in lock-step with what the audio
  actually says; it's the source when re-recording / re-synthesizing and the
  reference for translating the spoken text to a new language. Not consumed by
  the build.
- `audio/dialog/<lang>/<phase>-<n>.alaw` — the **dialog clips** of the
  interactive answer bot (#429, `ab_mode=dialog`): raw A-law like the
  announcement, one short sentence each, with a `<phase>-<n>.txt` transcript
  next to it (same rules as the announcement's), generated by
  `scripts/tts-dialog.py`. The five phases are `hello`, `who-is-there`,
  `am-aparat`, `question` and `cant-hear-you` (the flow is in
  `main/dialog.h`); each has 1..32 numbered clips (`question-1.alaw`,
  `question-2.alaw`, …), of which the device picks one at random, never the
  same twice in a row. Adding a variant is adding a file and republishing the
  audio channel — no firmware change. A locale is published only with **all
  five** phases; otherwise devices fall back along `ui_lang → en → de`.
- `l10n/` — the **translation project** (see "Translating" below):
  - `mail/mail_<lang>.arb` — status-mail strings. `mail_de.arb` is the single
    normative German source (edit it directly); the other `mail_<lang>.arb` are
    its translations. Its English translation `mail_en.arb` is baked into the
    firmware as the offline fallback (stripped to JSON at build,
    `main/CMakeLists.txt`), consumed by `main/mail_i18n.c`. Values use ICU
    `{name}` placeholders (never `printf` specifiers) and may contain `<b>` tags.
  - `ui/ui_<lang>.arb` — web-UI strings. `ui_de.arb` is the single normative
    German UI source (edit it directly — nothing is duplicated in
    `index.html`); the other `ui_<lang>.arb` are its translations. Its English
    translation `ui_en.arb` is baked into the firmware as the offline fallback
    (most widely understood; stripped to JSON at build, `main/CMakeLists.txt`)
    and served at `/api/i18n/ui` whenever the active locale's pack is missing.

## Translating (development time)

Reuses `de.haumacher:auto-translate-arb` — the **same Gradle plugin the mobile
app uses** (`phoneblock_mobile`). Outputs are committed; no translation runs at
release.

The DeepL key is supplied the **Gradle** way — `serverId = 'deepl'` in the
`build.gradle` files names the Gradle property `deepl.apiKey`, which belongs in
your user-global `~/.gradle/gradle.properties` (never in a committed
`gradle.properties`):

```properties
deepl.apiKey=YOUR_DEEPL_API_KEY
```

`DEEPL_API_KEY` in the environment works as a fallback. This is a *different*
credential store from the Maven-side translation of the web app's
`Messages_*.properties`, which reads the `deepl` server from
`~/.m2/settings.xml` — the same key, kept in both places.

Needs Gradle 8.x (the plugin's `plugins {}` block does not load under the
Gradle 4.x some distributions still package as `gradle`).

```bash
# Edit the German sources directly: l10n/mail/mail_de.arb and l10n/ui/ui_de.arb.
# Then translate both projects (mail + ui) into every target locale:
cd i18n/l10n && gradle translateArb

# 3. Review + commit the updated l10n/**/*_<lang>.arb.
```

Edit German only: `l10n/mail/mail_de.arb` and `l10n/ui/ui_de.arb`. A new
locale: add it to `targetLangs` in `l10n/mail/build.gradle` +
`l10n/ui/build.gradle` and to `languages.txt`.

### Dialog clips: speaking the sentences

The dialog sentences are an ARB project like the others
(`l10n/dialog/dialog_de.arb`, keys `<phase>_<n>`, translated by
`./gradlew translateArb`). No sentence may contain "Ja"/"yes" in any
language: a recorded "yes" can be abused as consent. `scripts/tts-dialog.py`
speaks them through ElevenLabs (the API key from `ELEVENLABS_API_KEY` or
`elevenlabs.apiKey` in `~/.gradle/gradle.properties`) with the voice and
model fixed in the script (`VOICE = "Leonie"`, `MODEL = "eleven_v4"`;
`ELEVENLABS_VOICE` / `ELEVENLABS_MODEL` override them for a trial). It keeps
a compact `.mp3` master next to each clip and records the speaker in
`<lang>/voice.json`; a locale spoken by another voice or model is
regenerated as a whole. Every `.alaw` is converted locally from that master: trimmed,
normalized to a common speech level, then A-law encoded.

```bash
../scripts/tts-dialog.py                 # (re)synthesize changed sentences only
../scripts/tts-dialog.py --convert-only  # re-encode from the masters, no API calls
```

The `.txt` next to a clip is the cache key, so a run after editing one
sentence costs one request. Commit masters, clips and transcripts together,
then publish with `audio-assets.sh` (below).

## Asset kinds & CDN layout

Two channels, both under `https://cdn.phoneblock.net/dongle/firmware/`
(`CONFIG_PHONEBLOCK_OTA_BASE_URL`):

| Kind | Path | Source | Published by | Fetched by |
|------|------|--------|--------------|------------|
| mail string pack | `<version>/i18n/mail/mail-<lang>.json` | `l10n/mail/*.arb` | `i18n-assets.sh` (by `release.sh`) | firmware |
| web-UI pack | `<version>/i18n/ui/lang-<code>.json` | `l10n/ui/*.arb` | `i18n-assets.sh` (by `release.sh`) | firmware, served at `/api/i18n/ui` |
| announcement audio | `audio/v<N>/announcement-<lang>-<sha8>.alaw` | `audio/announcement-*` | `audio-assets.sh` | firmware, unless an own recording or dialog mode |
| dialog clips | `audio/v<N>/dialog-<lang>-<tier>-<sha8>.bin` | `audio/dialog/<lang>/` | `audio-assets.sh` | firmware, only while `ab_mode=dialog` |

Each channel has its `manifest.json`; every asset is `{path, sha256, bytes}`
and checked against the SHA-256 after download. The **string packs** are tied
to the firmware version: the device fetches the subtree of the version it runs,
so an older release in the field is never affected by a newer one's key
changes. The published packs are the ARB files with their `@key` metadata
stripped (plain key→string JSON).

### Audio channel

The audio is not tied to a firmware version: the clip sets are too large to
republish with every release, and new sentences, voices or locales should
reach the fleet without one. The firmware reads exactly the channel of the
audio format it understands, `audio/v<N>/manifest.json` with
`N = AUDIO_FORMAT_VERSION` (`main/audio_manifest.h`), and re-checks it once a
day (with jitter; an unchanged manifest costs one GET and no download):

```json
{ "format": 1,
  "assets": {
    "de": { "announcement": { "path": "announcement-de-59007339.alaw", "sha256": "…", "bytes": 78762 },
            "dialog": [ { "path": "dialog-de-s-de522f20.bin", "sha256": "…", "bytes": 117995 },
                        { "path": "dialog-de-m-01253f03.bin", "sha256": "…", "bytes": 221243 },
                        { "path": "dialog-de-l-6654dbed.bin", "sha256": "…", "bytes": 489075 } ] },
    … } }
```

**Content updates republish `v<N>` in place** — `scripts/audio-assets.sh`.
File names are content-addressed (`<sha8>` = the first 8 hex digits of the
file's SHA-256), so an upload never replaces a file a device may be
downloading; the files go up first, the manifest last via posix-rename
(atomic), and only then are files removed that neither the new nor the
previous manifest names — a device that read the previous manifest a moment
ago still finds its files.

**Raise `N` only for an incompatible change** — one that firmware reading
`v<N>` could not handle:

- the manifest schema (a required field renamed, retyped or removed, a kind
  moved); adding fields or kinds is compatible — readers ignore what they do
  not know;
- the dialog file's header layout (`main/dialog.h`; a new `version` byte in
  it is such a change, extra phases after the five are not);
- the codec or sample format (A-law 8 kHz → anything else);
- the meaning of a tier's limits (`STORAGE_DIALOG_TIER_*`) in a way that
  would make a device download a set it has no room for.

A new `N` is a new directory: `v<N-1>` stays published as long as firmware
reading it is in the field (a content change for it is published from a
checkout of the last commit with that format — `audio-assets.sh` writes the
`N` of its own tree). Publish `v<N>` before the first firmware release that
reads it.

Firmware up to 1.7.0-beta7 reads its announcement from its own versioned
bundle (`<version>/i18n/audio/announcement-<lang>.alaw`); those bundles stay
on the CDN untouched. Releases from now on carry only the string packs.

### Dialog sets: one file, size tiers

The dialog clips of a locale are published as **one file** per size tier — on
the dongle's SPIFFS every file costs index pages and GC relocations, and many
small files drove the storage simulator (`test/test_storage_sim.c`) into GC
failures that one file of the same size does not. The file starts with its
clip table (header format in `main/dialog.h`: magic `PBDS`, version, the
clips per phase and each clip's offset and length), covered by the same
SHA-256 as the audio after it.

A full set (36 clips, 440–570 KB) does not fit every device, so up to three
**tiers** are published per locale, each the longest prefix of one priority
order that fits its limit — first clip 1 of every phase, then the further
`question`, `cant-hear-you`, `am-aparat`, `hello` and `who-is-there` clips:

| Tier | Limit | For |
|------|-------|-----|
| `s` | 128 KiB (`STORAGE_DIALOG_TIER_S`) | 4 MB boards, 640 KB storage partition |
| `m` | 224 KiB (`STORAGE_DIALOG_TIER_M`) | 16 MB boards (ESP32-S3), 1 MB storage partition |
| `l` | all clips | the Linux port |

A tier with the same clips as a smaller one is not published; a locale whose
minimum set (one clip per phase) exceeds `s` stops the publish. The limits are
read from `main/storage_budget.h`, where the simulation that validates them is
described. The device takes the largest tier within its budget
(`storage_dialog_budget()`), **as a whole** from the first locale of its
`ui_lang → en → de` chain that has one (never mixed across languages), stores
it as `dialog-<lang>.alaw` plus a `dialog.idx` naming the locale, written
once the file is verified and its header valid (`main/dialog_store.h`), and
removes it when `ab_mode` goes back to `announcement` or the chosen locale or
tier changes. In dialog mode the set takes the place of both announcements:
the localized one is neither downloaded nor kept, and switching to dialog
deletes an own recording (a new one can be uploaded in announcement mode
only). The set is a rarely written asset in the storage budget, ahead of the
community blocklist. A manifest must stay below the firmware's 12 KB fetch
buffer (`MANIFEST_CAP` in `main/i18n_sync.c`; the audio channel's is ~7 KB
for 14 locales).

**The manifest is not signed** — unlike the OTA manifest. The per-asset SHA-256
protects against a truncated or corrupted transfer, not against a hostile CDN:
transport trust is HTTPS plus the cert bundle, and the worst a substituted
bundle achieves is wrong text or wrong audio. That is a deliberate
trade for the development loop below, which would otherwise need the release
key for every string change. Consequence for anyone consuming a pack: treat the
strings as untrusted input — never interpolate one into HTML unescaped (see how
`status.info` is assembled in `main/web/index.html`).

## Publishing

**String packs ship with the firmware**: `scripts/release.sh` calls
`i18n-assets.sh` for the release version, publishing the `.bin` and its
co-located packs together. To (re)publish them on their own:

```bash
# Dry run: assemble locally, print the upload commands.
../scripts/i18n-assets.sh --dry-run

# Standalone real publish for a firmware version:
../scripts/i18n-assets.sh --version 1.5.0
```

`--version` MUST equal what the device reports as `firmware_version`, minus its
git-describe dev suffix. Omit it and the script derives exactly that from the
workspace (same `git describe` + same normalization as the firmware), which is
what makes the dev loop below work. No credential beyond CDN ssh access is
needed — no translation and no signing run here. A missing pack (UI or mail)
degrades to the firmware's embedded English fallback for that surface.

**Audio is published on its own**, whenever it changes — no firmware version
involved:

```bash
../scripts/audio-assets.sh --dry-run     # build, print the upload steps
../scripts/audio-assets.sh               # publish audio/v<N>/
```

Devices pick a change up on their next daily check (or at once on a language
or answer-bot mode switch).

## Testing an unreleased bundle on a device

The device asks for **its own version's** bundle, so a dev build looks for the
tag it was built from — not for the release you have in mind. `git describe`
strips only the `-<N>-g<hash>[-dirty]` suffix, so a build 49 commits past
`dongle-v1.5.2` asks for `1.5.2/i18n/`, and a bundle published as `1.6.0-rc1`
would simply be ignored.

So make the tag say what you want **before building**, then publish bare:

```bash
git tag dongle-v1.6.0-beta1              # local is enough; do not push a
                                         # throwaway tag that could collide
                                         # with the real release tag
cd phoneblock-dongle/firmware
./scripts/i18n-assets.sh                 # derives 1.6.0-beta1 from the tag
idf.py reconfigure && idf.py build       # reconfigure: PROJECT_VER is computed
                                         # at configure time and a new tag
                                         # changes no file, so a plain build
                                         # would silently keep the old version
```

One bundle then covers the whole development period — the commit count and
`-dirty` are stripped, so every later build on that line resolves to the same
tag. `git tag -d dongle-v1.6.0-beta1` when done.

### Unpublished audio

The audio channel has no per-build copy: what is published is what every
device of that format gets. To try audio that is not published yet, push it
straight to a device in dialog mode — `scripts/dev-i18n-push.sh --kinds dialog`
builds the set with `audio-assets.sh --no-upload` and uploads the tier the
device would download (`POST /api/dev/i18n?kind=dialog`). It stays until the
device's next sync (at the latest the next daily check).
